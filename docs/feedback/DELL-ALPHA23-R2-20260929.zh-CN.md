# Agent Channel：DELL 全过程试用问题与产品迭代报告

日期：2026-09-29

面向：Agent Channel 产品负责人
性质：独立用户环境的安装、接入、试用及本机热修复盘；不是原版发布验收通过证明。

## 1. 先给结论

**Agent Channel 的隔离底座表现出价值，但尚未跑通“两个已有产品对话直接使用、持续完成真实开发”的完整链路。** 本轮主要困难不是“能不能启动两个容器”，而是安装耗时不可控、安装回执不可靠、旧新接线混存、长对话没有加载新工具，以及真实 4K 画面不适配。这些断点让用户和主 agent 花了大量精力维护工具，而不是推进产品。

DELL 最终通过派生安装包及本地热修，运行了两个 Linux 微信开发者工具频道。独立 MCP 桥的截图、合成输入隔离、暂停/人工接管、快捷键和一次容器重启恢复有证据。但产品A、产品B的既有对话没有完成新 MCP 接入，更没有完成两个真实项目的同时编译和验收。因此不能据此宣称已解决“两个产品抢电脑”，也不能宣称节省了时间或 token。

下一轮应优先修完整用户旅程，而不是继续堆频道数或新功能：**原包可靠安装 → 当前客户端明确接通 → 看得清、点得准 → 两个合法测试项目独立完成任务 → 人工随时接管并恢复。**

## 2. 用户原本要解决什么

用户在 DELL 同时推进产品A和产品B。两个主对话涉及浏览器、微信开发者工具及 Computer Use，使用同一个 Windows 桌面时容易互相争抢焦点，用户也难以正常操作电脑。

期望体验是：

1. 安装 Agent Channel 后，每个产品获得一个可识别、可持续使用的独立工作空间。
2. 既有主对话保留产品上下文，直接使用对应频道，不需要重新搭建组织或搬运大量聊天。
3. 两个任务同时操作各自工具，互不改动对方页面、工程和输入。
4. 用户继续使用 Windows；需要介入时快捷切换，暂停 AI、人工操作，再交回 AI。
5. 软件能清楚告诉用户：安装到哪一步、哪个对话已连上、哪个工程正在运行、哪里需要本人配合。

这次最重要的产品价值指标，不是“容器数量为 2”，而是用户能否少协调、少排障，让两个真实任务顺畅完成。

## 4. 全过程：用户旅程在哪里被打断

### 阶段一：包校验完成，但第一次安装被在线下载拖住

先按说明阅读 README、安装文档和 AI 接入文档，取得 alpha.23 r2 并校验。前置检查通过后，原包开始安装 Debian 依赖：217 个新增软件包，下载量约 219 MB，现场速度约 30 KB/s。等待后停止了这一轮，因此原包首装没有完成。

为了继续验证产品，另建派生测试副本，把 Debian 源换为镜像源。相同容器内的 1 MB 下载对比，原源约 21.6 秒，镜像约 0.4 秒。这是本机当时的网络样本，不代表所有地区或时间都如此。

随后微信开发者工具的固定 `.deb` 包又成为瓶颈：约 186 MB / 195,249,680 bytes，GitHub 下载约 35 KB/s。按当时速度估算可能超过 90 分钟，不是实际完整等待 90 分钟。最终以 16 段并行下载组装，核对固定 SHA256 后才继续。

**体验问题：**用户以为下载好 ZIP 就能安装，实际还要经历多层大文件在线下载。普通用户缺少清楚的阶段、耗时预期和可靠恢复入口；本轮需要懂 Docker、网络下载和校验的人介入。

### 阶段二：服务其实启动了，安装回执却说失败

派生副本的 Firefox 基础安装能运行，但输出出现 `installed-start-failed` 和 `Invalid JSON primitive: .`，同时退出码却为 0。检查时两个频道及查看器已经运行。

这使“安装器说失败、进程看起来成功、命令又返回成功”同时存在。用户或 agent 无法决定该重装、重启还是继续，容易触发重复安装或错误修复。

接着进行微信离线升级，又遇到 PowerShell 5.1 对缺失镜像探测的错误处理：`docker image inspect` 在镜像不存在时返回错误，本应走构建分支，却被严格错误行为提前中断。派生脚本修正这个探测后，才完成微信镜像升级。

### 阶段三：本机旧安装与新安装发生碰撞

DELL 之前有试验版，旧、新安装使用同一个 Compose project 名 `qicheng-agent-channels`。新安装重建了旧的已停止容器。总控事先保留了可恢复镜像，未观察到数据丢失，但不能把这种保全工作留给最终用户临场判断。

### 阶段四：新 MCP 已注册，但老对话仍然只看见旧工具

接入时，`Connect-Codex.cmd` 的交互确认在工具驱动的终端里没有消费输入，取消后改用安装脚本的 `-Apply` 接口完成注册。这不证明人手双击场景也坏了，但自动部署路径不够顺。

新服务 `qicheng_lite_1/2` 写入配置后，独立桥进程测试正常；然而产品A、产品B的既有 Codex 长对话仍只暴露旧的 `qicheng_channel_1/2`。产品A调用旧工具得到 HTTP 401，且旧桥把它解释成“需要人工开启 agent 模式”。这导致一度把接线或认证问题误当成接管状态问题，用户被要求做无效操作。

安装文档实际上已有“注册后重启客户端”的提示。问题不是完全没写重启，而是**缺少旧版迁移、当前会话是否加载、旧工具不能继续用、重载后如何证明接通**的完整说明和探针。不能只凭配置成功就向产品对话宣布可用。

### 阶段五：总控测出隔离成立，真实产品使用仍卡在入口

总控用两个独立新桥进程进入游客模式，在两个频道分别输入 `AC-DELL-CH1` 和 `AC-DELL-CH2`，截图各自只出现自身字样。暂停和人工接管时输入被拒绝，恢复 agent 后输入成功。

这些证明隔离和控制原语有一定可用性，但并不是两个产品 PM 已经使用新频道开发。没有导入真实项目，没有微信账号登录、编译、预览、上传或真机验收。两个产品既有对话的问题仍停留在“实际拿不到新工具”。

### 阶段六：静态自测为绿，用户却发现 4K 按钮挤在一起

用户现场指出“功能按键都缩到一起”，暴露了此前自测没有覆盖的真实显示缺陷。主屏 4K / 250% 下，Windows 报告活动窗口 DPI 为 240，但 WinForms `DeviceDpi` 为 96。原按钮物理尺寸只有 110×42，画面放大也受限，操作区域显得很小。

总控制作本地 DPI 修正，先独立启动候选查看器验证。第一次额外手工放大字体又造成截字，截图检查发现 WinForms 已经缩放了文字，遂撤回字体倍乘，只修布局和画面缩放。最后实际按钮达到 275×105，主屏截图未见截字，热键和接管回归通过。

这说明测试不能停在布局函数返回 true，还要看真实窗口、真实文字和实际点击。当前热修没有完成第二屏视觉验收、长期人工操作及内层微信工具的完整适配。

## 5. 问题清单及可执行验收标准

这里的 P0 指“下一轮完整试用前应解决的阻断项”，不是安全事故等级。

### AC-01｜P0：首次安装的网络依赖过重、恢复成本高

**证据：**219 MB Debian 依赖下载慢；约 186 MB 微信包下载慢；需要换源、并行下载、基础安装后再离线升级。

**影响：**首次价值出现太晚。用户不知道是在正常等待还是卡住；重试可能重复下载。所谓离线升级不能替代第一次安装的完整离线/缓存路径。

**建议：**明确列出 ZIP 之外还需下载什么；分阶段显示进度、速度、缓存命中、失败原因；允许可信且校验一致的备用下载路径、断点续传及缓存复用。预构建镜像或离线材料应先核实分发许可和版本校验，不简单把第三方内容全塞进包。

**验收：**限速、断网再恢复、下载中断后重试三个场景不重复已验证材料；失败能指出具体下载项；普通用户按文档能完成原包安装，无需现场改 Dockerfile。

### AC-02｜P0：预期的“镜像不存在”被当成致命异常

**证据：**Windows PowerShell 5.1 下，安装脚本 `docker image inspect` 探测缺失目标镜像时被 `$ErrorActionPreference='Stop'` 中断。

**当前处理：**只在派生副本调整该探测，保留退出码判断和原错误策略恢复；不是全局关闭错误检查。升级后返回 started、两频道正常。

**建议与验收：**明确区分“未安装，需要构建”和“Docker 不可用/权限异常”；覆盖完全无镜像、只有基础镜像、已安装重复执行、Docker 未启动四种情况，在 PowerShell 5.1 上实测。缺镜像应继续正确分支，真正失败应明确终止。

### AC-03｜P0：安装状态、启动状态与退出码互相矛盾

**证据：**`installed-start-failed`、`Invalid JSON primitive: .`、退出码 0，而服务实际已运行。

**原因置信度：**结构化 JSON 输入混入启动/Compose 文本是待复现的原因推断；不应直接当成已定位到唯一代码行。

**建议：**机器回执与人类日志分离；记录阶段、实际健康检查、可恢复动作和有意义的退出码。不要依据最后一条日志判断整次安装。

**验收：**正常成功、构建失败、启动失败、服务成功但回执解析失败分别有一致状态；agent 可以从回执可靠选择下一步，不需靠猜进程。

### AC-04｜P1：校验字段不能清楚表达已经验证了什么

**证据：**离线升级后 `imageContentVerified=true`，但 `wechatPackageVerified=false`；本轮下载包已由总控按固定 SHA256 手工核对。

**影响：**无法判断 false 是未运行校验、校验失败还是该路径不适用。不能把手工校验结果反写成安装器已验证，也不能据此断言所有产品校验都缺失。

**建议与验收：**给出 verified / failed / not_checked / not_applicable 等明确状态、对象、期望/实际摘要和来源；在线、离线、缓存三条路径回执语义一致。

### AC-05｜P0：旧安装识别和迁移不足

**证据：**新旧 Compose project 同名，重建旧停止容器；总控另做恢复镜像。旧源目录和 token 保留，新频道使用独立 home 卷。

**影响：**用户可能不知道安装会影响另一份试验环境；“重装”与“并行安装”边界不清。

**建议与验收：**安装前列出冲突的项目、容器、卷和配置，提供明确的复用/迁移/另装方案；保留用户数据和回滚信息。已有旧环境时不应静默把它当成本次安装资产处理。测试停止旧环境、运行旧环境、重复升级三个场景。

### AC-06｜P1：交互安装路径与自动部署路径不一致

**证据：**`Connect-Codex.cmd` 中 `choice` 在本轮 PTY 工具输入下没继续；改用注册脚本 `-Apply` 成功。

**边界：**未证明人工终端或双击操作有相同缺陷。

**建议与验收：**保留人工预览/确认，同时文档提供明确的非交互部署参数、预览结果及可检测退出码；无可用交互输入时快速说明，而不是无限等候。两种路径产生同一组可回滚配置变更。

### AC-07｜P0：配置写入不等于长对话已经接入

**证据：**独立新桥正常，产品A和产品B当前工具列表却没有 `qicheng_lite_1/2`。旧新服务同时存在。产品A采样时发现旧桥进程仍在，未发现安装版新桥进程。

**影响：**用户以为“安装好了，可以继续”，实际业务窗口无法使用。反复让主模型读 Skill、改提示词或切 agent 模式不能解决工具尚未加载。

**建议：**接入向导分别标记“配置已写入”“客户端已加载”“当前会话状态读取成功”“输入/截图成功”。识别旧服务名和路径，提供有备份的迁移步骤与安全检查点重载指引。旧长任务运行时不要强行关闭客户端。

**验收：**一个原先连着旧版的长对话，按说明保存状态、重载后，确实调用安装版新桥并取得身份回执。不能以 `mcp list` 或配置文件有条目作为最终成功。具体客户端版本是否支持热加载需实测，不承诺通用无重启切换。

### AC-08｜P0：401 被错误解释为“请开启 AI 控制”

**证据：**产品A调用旧 state/screenshot 返回 HTTP 401。旧桥把 HTTPError 统一映射成需要人工启用 agent 模式的提示。最初反馈据此误引导，后已更正。

**正确理解：**401 不能证明频道处于 paused/human。认证失败时控制状态应记为未知，优先核对正在调用哪套服务及认证配置，不要求用户来回点接管按钮。

**建议与验收：**区分认证失败、服务不存在/连接失败、paused/human 的输入拒绝及内部错误。回归至少覆盖：有效认证+agent、有效认证+paused、有效认证+human、无效认证401、旧客户端接新安装。每种错误都给准确且不泄露凭据的下一步。

### AC-09｜P1：产品、服务名、频道分配与版本身份缺少统一表达

**证据：**现场同时出现 Agent Channel、Qicheng Lite、`qicheng_channel_*`、`qicheng_lite_*`。产品B回件指出历史能力 README 分配“产品B 频道一、产品A频道二”，与本轮指定“产品A一、产品B二”相反。该历史文本问题来自产品B回件，不是本报告再次独立核验。

**影响：**agent 有工具却不确定是否用对；共享方法中的旧频道号污染本轮任务。频道编号不应天然绑定一个产品。

**建议与验收：**提供可核验身份回执：产品版本、桥版本、频道 ID、当前模式、可用能力；项目/任务绑定有证据才显示，否则明确未绑定。当前会话分配应由一个权威记录表达，文档示例不作为固定路由。新旧安装并存时能直接分辨，不靠模型从名称猜测。

### AC-10｜P0：4K / 250% 下查看器尺寸不适配，自测未捕捉

**证据：**OS DPI=240、WinForms DeviceDpi=96；原按钮110×42物理像素。用户明确反馈按钮挤在一起，而原 `picture_layout` 自测为 true。

**当前本机修复：**布局优先读取 `GetDpiForWindow`，句柄建立和 `WM_DPICHANGED` 后重布局；画面缩放上限放宽至2.5，仍等比适配可用区域；不额外倍乘字体。主屏按钮变为275×105，实际截图未见截字。

**建议与验收：**上游吸收并独立复验，不把本机补丁直接认定为完整解决。覆盖100%/125%/150%/250%、4K、小窗口及不同DPI跨屏；检查文字完整、按钮可点击、布局不重叠、画面与输入坐标一致。必须有真实截图和点击证据，不能只有几何单测。

### AC-11｜P1：外层画面放大不等于内层应用可用

**证据：**热修扩大了频道画面，内层微信开发者工具仍是未最大化窗口。第二屏 UIA 边界正常，但截屏方法得到黑图，视觉结论未知。

**注意：**不能把黑截图写成产品黑屏故障；它也可能是取屏方式问题。本轮没有证据确认原因。

**建议：**明确区分宿主DPI、查看器缩放、Linux桌面分辨率和应用窗口尺寸；提供易懂的适应窗口/原始比例/缩放与窗口最大化引导。查看器当前按鼠标所在屏打开，应让用户知道这一策略，评估记住目标屏或可选屏幕。

**验收：**两屏分别能看清内层应用，最大化后关键区域可达；缩放后点击命中实际控件；来回切屏不丢工具栏，不靠修改Windows全局缩放才能使用。

### AC-12｜P1：切换与恢复的反馈不够完整

**证据：**Alt+2/3 合成切换通过；Alt+1 回宿主在750ms采样时尚未完成，后续约2秒观察到返回，测试改为最多等待3秒。只有频道一容器重启及文件留存通过。

**边界：**没有快捷键延迟分布；不能宣称每次都慢或瞬时完成。宿主重启、页面恢复、暂停状态保持、人工物理热键尚未验收。

**建议与验收：**切换进行中有轻量反馈，返回目标明确；定义哪些状态持久保存、哪些重启后重建。在实际Windows重启后检查频道身份、数据、模式、MCP可用性及恢复提示，不能用快捷方式存在代替开机实测。

### AC-13｜P0：缺少“从游客页到真实工程”的最后一段验收

**证据：**两频道仅进入游客空项目页，未完成合法业务项目导入和编译。宿主Windows微信工具不等于Linux社区版微信工具，Windows Computer Use、USB真机也没有因此自动可用。

**影响：**演示两个桌面容易让人误以为已满足实际微信开发需求，但工程路径、依赖、登录、工具兼容、构建输出及人工协作仍可能出现新阻断。

**建议与验收：**明确支持矩阵和任务起步方法，选择两个授权的测试工程，分别完成一次有真实输出的编辑/编译/检查任务。若某能力仅支持宿主或需要账号/硬件，应明确提示并提供合理接续，不把Linux频道包装成所有电脑操控能力的替代。

## 6. 两个产品窗口的独立反馈，不能混算

| 观察者 | 实际做到 | 实际发现 | 没有做到 |
|---|---|---|---|
| DELL总控 | 新桥独立进程状态、截图、合成输入；查看器接管、切换、DPI修复 | 安装链多处失败；真实4K缺陷；底层隔离初验成立 | 未使两个原产品对话完成新桥业务验收 |
| 产品A主对话 | 调旧state/screenshot，两轮均401；检查工具与进程；形成项目报告 | 长对话只暴露旧工具；错误提示误导；注册状态与运行状态不一致 | 无新频道截图或输入、无真实工程编译 |
| 产品B主对话 | 阅读Skill、检查本轮工具列表；另对宿主做只读应用枚举 | 看不到新lite工具；历史频道映射可能误导；接线身份不清 | 没调旧频道state/screenshot，不能称亲测401；没做频道输入或业务验收 |

产品B特别澄清：它转述的401来自总控及产品A，不是它自己的试验；它没有主动激活宿主微信窗口或点击，但也没有独立的连续焦点遥测，所以不能升级为“已证明全程不抢焦点”。

产品A采样发现14个旧桥进程（每频道7个），这是应进一步诊断的旧会话/进程存量，不足以证明内存泄漏或可以全部终止。不能以清理之名中断其他在途工作。

## 7. 哪些不应归罪于 Agent Channel

1. 产品B本来的 Docker/Node 构建和依赖下载，不是通过 Agent Channel 完成的测试，也不能直接算作本产品性能问题。
2. 宿主两个同名微信窗口无法仅凭标题绑定源码、9421只读连接失败，是产品B的宿主工具现象；本轮没证据证明由Agent Channel引起。
3. 总控会话没有启用某个Windows CUA工具，不代表所有会话都没有电脑操控，更不证明Linux频道能替代它。
4. 测试端到产品维护端的远程连接不可用，是另一条协作链问题，不是本产品频道故障。
5. 未提供登录和合法测试项目导致业务验收未做，这部分是验收前提缺失。产品仍有责任把前提和起步方法说清楚，但不能直接判定编译功能失败。
6. 第二屏黑截图是采集结果不确定，不能当成用户已看到黑屏。
